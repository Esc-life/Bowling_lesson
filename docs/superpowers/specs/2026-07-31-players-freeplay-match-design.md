# 플레이어 · 자유 연습 · 다인 매치 설계

작성일 2026-07-31. 대상 코드베이스: 3D 볼링 게임 + 초등 교육용 튜토리얼 (`PLAN.md`, `STATUS.md`).

## 무엇을 만드는가

사용자 요청 세 가지:

1. 배워야 할 내용을 모두 배운 다음 자유 연습
2. 싱글 플레이 외에 멀티 플레이
3. 계정까지는 아니어도 플레이어 이름 저장

## 범위 — 이 스펙은 1·2단계까지다

멀티플레이는 **온라인 실시간 대전**으로 확정했다. 세 요청을 한 덩어리로 만들 수 없다.
규모 때문이 아니라 의존 관계 때문이다.

- 지금 `FrameMachine`/`Scorecard`는 1인용 전제다. 온라인 대전은 "여러 명이 번갈아
  던지는 매치" 개념이 규칙 계층에 먼저 있어야 그 위에 네트워크를 얹을 수 있다.
- 플레이어 이름은 멀티플레이의 선행 조건이다. 누가 던질 차례인지 표시해야 한다.
- 자유 연습은 위 둘과 독립이고 작다.

| 단계 | 내용 | 서버 |
|---|---|---|
| 1 | 플레이어 이름 저장 + 자유 연습 모드 | 불필요 |
| 2 | 다인 매치 구조 (같은 기기에서 번갈아 하기로 먼저 동작) | 불필요 |
| 3 | 온라인 실시간 (2단계 매치 상태를 네트워크로 동기화) | Supabase Realtime |

**이 스펙은 1단계와 2단계를 다룬다.** 3단계는 별도 스펙으로 브레인스토밍한다.

2단계는 3단계를 위한 버리는 작업이 아니다. 온라인 매치도 같은 매치 상태머신을 쓰고,
서버 없이 테스트할 수 있는 버전이 있으면 3단계 디버깅이 훨씬 쉽다.

### 이 스펙에서 제외한 것

- 온라인 대전 일체 (3단계)
- 관찰 도구(슬로모션·궤적 리본·오일 구간·핀 번호)의 자유 연습 내 노출 — 튜토리얼 전용으로 유지
- 플레이어의 손 설정을 나중에 바꾸는 UI — 만들 때 정하고 그대로 둔다
- AI 상대
- 점수 기록 순위표 · 통계

## 1. 데이터 — 누가 플레이하는가

```
bowling3d.players.v1
  players: [{ id, name, handedness, progress: ProgressState, createdAt }]
  lastPlayerId: string | null
```

기존 저장 키와의 관계:

| 키 | 지금 | 앞으로 |
|---|---|---|
| `bowling3d.progress.v1` | 기기 하나에 진행률 하나 | 폐기. 플레이어별 `progress`로 이동 |
| `bowling3d.settings.v1` | handedness + 난이도 + 관찰 옵션 | handedness 제거. 나머지는 전역 유지 |
| `bowling3d.players.v1` | — | 신규 |

### handedness를 플레이어로 옮긴다

왼손잡이와 오른손잡이가 한 PC를 쓰는데 손 설정이 전역이면 서로 계속 덮어쓴다.
**플레이어를 만들 때 이름과 함께 손을 고르고, 그 값이 그 플레이어에 저장된다.**

대전 중 턴이 넘어갈 때마다 그 사람의 손으로 `Game.applySettings()`를 다시 부른다
(이미 있는 메서드다).

전역 `settings`에는 손과 무관한 것만 남는다 — 난이도, 관찰 표시 옵션.

### 기존 저장 데이터 이관

앱 시작 시 `players.v1`이 없고 `progress.v1`이 있으면, 이름만 물어보고 그 진행률과
`settings.v1`의 손을 첫 플레이어로 옮긴다. 지금까지 쓰던 학생이 진도를 잃지 않는다.
이관 후 `progress.v1`은 지운다.

`players.v1`도 `progress.v1`도 없으면(완전한 첫 실행) 목록을 건너뛰고 바로 새로 만들기
화면을 띄운다. 빈 목록을 보여 줄 이유가 없다.

### 삭제

목록의 각 이름에 삭제 버튼. 진행률이 함께 사라지므로 **2단계 확인**을 둔다
(영역 메뉴의 초기화가 이미 같은 방식이므로 패턴을 맞춘다).

마지막 한 명을 지우면 플레이어가 0명이 되고, 새로 만들기 화면으로 간다.

### 이름 규칙

- 1~12자, 앞뒤 공백 제거
- 빈 이름 불가
- 중복 이름 불가 — 대전 참가자 목록에서 누가 누구인지 구분되지 않는다.
  같은 이름을 넣으면 "이미 있는 이름이에요"라고 알린다.
- 깨진 저장 데이터는 조용히 기본값으로 되돌린다 (`Progress.sanitize`와 같은 방침)

## 2. 규칙 계층 — `rules/MatchMachine.ts` (순수, 신규)

`FrameMachine`을 사람 수만큼 만들어 두고, 턴 순서만 관리하는 순수 클래스를 얹는다.
**`FrameMachine`은 한 줄도 건드리지 않는다.**

```
MatchMachine(players: {id, name, handedness}[], totalFrames)
  players[i].machine: FrameMachine    ← 사람마다 하나
  currentPlayerIndex
  active                              ← 지금 차례인 플레이어
  throwBall() / beginSettling() / settle(pins)   → active.machine에 위임
  프레임이 끝나면(result.frameCompleted) 다음 사람으로 넘긴다
  모두 마지막 프레임을 끝내면 isMatchOver
  ranking                             ← 총점 내림차순, 동점은 공동 순위
```

턴 순서는 실제 볼링과 같다 — 각자 한 프레임씩 돌아가며 친다.

`Game`은 `machine: FrameMachine` 대신 `match: MatchMachine`을 갖고 `match.active`에
위임한다. **1인 경기 = 1명짜리 매치**라서 자유 연습과 대전이 같은 코드를 탄다.

턴이 바뀔 때 하는 일: 핀 10개 리셋 → 그 사람 손으로 전환 → "○○○ 차례" 배너.

### `Scorecard`의 프레임 수를 인자로 뺀다

대전은 사람마다 최대 10프레임씩이라 4명이면 투구 40~84회다. 지금 한 투구가 정지까지
2.8~5.7초 걸리므로(`STATUS.md` 실측) 한 매치가 10분을 넘길 수 있다. 초등 수업 한 차시로는
길다. **대전 시작 시 3 / 5 / 10 프레임 중에 고른다.**

이를 위해 `TOTAL_FRAMES = 10` 모듈 상수를 `Scorecard`의 생성자 인자로 바꾼다
(`new Scorecard(totalFrames = 10)`).

- 이 상수는 `Scorecard.ts` 밖에서 쓰이지 않는다 (확인함). 변경 범위가 파일 하나로 닫힌다.
- 코드가 이미 마지막 프레임을 `TOTAL_FRAMES - 1`로 일관되게 표현하고 있어 기계적 치환이다.
- 기본값이 10이라 인자 없이 부르는 기존 호출부와 테스트는 그대로 통과한다.

**중간에 끊는 방식(10프레임 카드를 만들고 N프레임에서 종료)을 쓰지 않는 이유:** 마지막
프레임에 스트라이크를 치면 보너스 투구가 없어 점수 칸이 빈칸으로 남는다. 아이들에게
"왜 마지막 칸만 비어 있냐"는 혼란을 준다. 프레임 수를 진짜로 줄이면 3프레임 경기의
3프레임도 10프레임 경기의 10프레임과 똑같이 동작해서, 배운 규칙이 그대로 적용된다.

## 3. 자유 연습 — 두 종류

**10프레임 정식 경기**는 1명짜리 `MatchMachine`이다. 점수판·게임 오버 그대로.

**연습 투구**는 프레임도 점수도 없는 얇은 세션이다. 매 투구 후 지정한 핀 배치로 리셋한다.
"무한 투구"와 "핀 배치 고르기"는 같은 세션이고, 후자는 여기에 **핀 10개를 클릭해 켜고 끄는
화면**을 붙인 것뿐이다(기본값은 10개 전부). 기존 `Game.setupDrill()`을 그대로 쓴다.

투구 결과 문구는 드릴과 같은 방침을 따른다 — 핀 일부만 세운 상태에서 `FrameMachine`이
계산한 "스트라이크!"는 틀리므로, 연습 투구 중에는 기본 배너를 끄고 "10개 중 7개"처럼
넘어뜨린 개수만 표시한다 (`STATUS.md`의 드릴 설계 메모와 동일한 이유).

## 4. 화면 흐름

```
앱 시작
  └ 플레이어 선택         목록에서 탭 · [+ 새로 만들기] · 각 줄에 [삭제]
      └ 새로 만들기 → 이름 입력 + 손 고르기 (한 화면)
          ↓
  홈 = 영역 메뉴
      ├ 배우기        A~E 영역, 진행률, 이어서 하기   ← 항상 열림
      ├ 자유 연습     🔒 18레슨 전부 수료해야 열림
      │    ├ 10프레임 경기
      │    └ 연습 투구 → 핀 배치 고르기(기본 10개) → 무한 반복
      └ 대전          🔒 참가자 전원 수료해야 열림
           └ 참가자 고르기 (2~4명) → 프레임 수 고르기 (3/5/10) → 매치
```

**가장 큰 변화:** 지금은 켜자마자 레인이 나오고 '배우기'가 우상단 버튼이었다. 이제 **홈이
영역 메뉴**가 되고 게임 화면은 거기서 들어간다. 방향이 뒤집힌다. `main.ts`의 부트스트랩과
`TutorialUI`의 진입 방식이 이 스펙에서 가장 많이 바뀌는 부분이다.

처음 쓰는 사람이 공을 던지기까지 레슨을 거쳐야 하지만, 드릴이 레슨 안에 있어서 공은 일찍
던진다 (A영역 이후 D영역 드릴).

### 잠금 표시

버튼을 **숨기지 않고** 자물쇠와 함께 보여 준다. 누르면 "18개 중 7개를 배웠어요. 다 배우면
열려요"라고 알린다. 목표가 보여야 동기가 생긴다. 감춰 두면 있는 줄도 모른다.

### 대전 참가자 고르기

목록에서 미수료자는 흐리게 + 자물쇠. 눌러도 선택되지 않고 "○○○는 아직 다 배우지
않았어요"라고 표시한다. 되는 줄 알고 골랐다가 시작 버튼에서 막히는 것보다, 고르는 순간
이유가 보이는 편이 낫다.

인원은 2~4명이다. 실제 볼링장 한 레인 기준이고, 점수판에 4줄까지가 화면에 무리 없이 들어간다.

### 딥링크

수업용이므로 `?lesson=` `?area=` `?hand=` `?debug=1`은 그대로 유지한다.
`?player=<이름>`을 더해 플레이어 선택 화면을 건너뛴다. 없는 이름이면 선택 화면을 그냥 띄운다.

## 6. 검증

| 대상 | 방법 |
|---|---|
| `MatchMachine` 턴 순서·순위 | 유닛 테스트. 2~4명, 스트라이크·스페어 섞인 매치, 동점 공동 순위 |
| 짧은 매치 | 유닛 테스트. 3·5프레임 경기의 마지막 프레임에 보너스 투구가 붙는지 |
| `PlayerStore` | 유닛 테스트. 생성·삭제·중복 이름·빈 이름·깨진 데이터 복구·**구버전 진행률 이관** |
| 해금 판정 | 유닛 테스트. 17/18은 잠김, 18/18은 열림, 참가자 중 1명 미수료면 대전 잠김 |
| 기존 183개 | 그대로 통과해야 한다. `FrameMachine`·점수 로직을 안 건드리는 것이 이 조건이다 |
| 타입·빌드 | `npm run typecheck`, `npm run build` |
| 화면 흐름 | 브라우저 실기. 이름 2개를 만들어 한쪽만 수료시키고 → 잠금 문구, 대전 참가 제한, 턴 전환 시 손이 바뀌는 것, 3프레임 매치 완주 |

### 위험

- **부트스트랩 방향이 뒤집힌다.** `main.ts`와 `TutorialUI`의 진입 경로가 가장 많이 바뀌는
  부분이라 회귀가 나기 쉽다. 딥링크 4종이 모두 살아 있는지 실기로 확인한다.
- **저장 스키마가 바뀐다.** 이관 코드에 버그가 있으면 기존 사용자의 진도가 날아간다.
  이관은 유닛 테스트로 먼저 고정하고, 이관 후에야 옛 키를 지운다.
- **대전 소요 시간.** 3/5/10 선택으로 완화하지만, 실기에서 4명 3프레임이 실제로 몇 분
  걸리는지 재 본다. 여전히 길면 기본값을 3으로 둔다.
